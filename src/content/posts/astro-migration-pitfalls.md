新站做完，域名也接上了。我以为最后一步就是刷新一下，结果无痕窗口一开，控制台整片红。

`net::ERR_ABORTED 503 (Service Unavailable)`，几十条，全是站内链接。

<img src="/pic/astro-503-console.webp" alt="浏览器控制台里整片 503 报错，站内链接全部变红" width="1066" height="724" loading="lazy" decoding="async">

普通刷新又是好的。能点开，但控制台一直在报。

## 只在预取时出现的 503

我先按最笨的办法排除。curl 直接打那些页面，八条路由全是 200。又压了三十次首页加二十条混合链接，五十个请求，一个 503 都没有。按这个结果，像是切域名那一刻的边缘抖动，过去就好。

过了一阵还在报。我让助手再测，这次带上浏览器的预取头。同一个地址，普通 GET 是 200，加上 `Sec-Purpose: prefetch` 就变 503，别的头怎么加都没事。只这一个头。

响应头里有答案。

```
Cf-Speculation-Refused: prefetch refused: disabled for worker requests
```

普通请求里还有一行。

```
Speculation-Rules: "/cdn-cgi/speculation"
```

到这就清楚了。Cloudflare 开着一个叫 Speed Brain 的东西，默认开着，会给页面塞一份预取规则，让浏览器提前把链接抓下来。我的站是 Worker 部署，Cloudflare 对 Worker 请求一律拒绝预取，怕预取触发副作用。浏览器每预取一次，边缘就回一个 503。

我自己又在这头加了一把火。Astro 的预取配置我开了 `prefetchAll: true`，策略是 viewport，意思是视口里看得见的链接全部预取。两套预取叠在一起，一整批链接齐刷刷 503。

有个反证挺有用。我另一个导航站也部署在 Cloudflare，同样是边缘项目，响应头里也有那行 Speculation-Rules，可它控制台干干净净。

<img src="/pic/nav-console-clean.webp" alt="另一个导航站的控制台，干干净净没有任何报错" width="1600" height="759" loading="lazy" decoding="async">

它是原生 JS 写的，根本没有主动预取。所以病根不光是 Speed Brain，我自己那套批量预取也脱不了干系。

解法是把 Astro 的预取改成保守的。

```js
prefetch: {
  prefetchAll: false,
  defaultStrategy: 'hover',
}
```

不再预取整个视口，只在鼠标悬停或者我显式标记的链接上预取。推上去，控制台的 503 就没了。

预取这个坑，说到底是两个默认值叠在一起。迁移里真正耗时间的，反而是前面那些看起来更基础的东西。

## 回到更基础的地方

第一个是 Node 版本。Astro 7 要 Node 22.23.4 以上，我机器上装的 22.22.2，差一点点。它不给你降级跑，直接拒绝。后来换了一个便携版 24，每次构建前把路径指过去。这一步不复杂，但报错信息不会告诉你换个 Node，它只会说版本不满足。

第二个坑更有迷惑性，构建显示成功，产物是半截的。

我在本地跑构建，结束的时候带一句报错，但退出还算正常。我没当回事，直到发现 sitemap 一直是旧的，搜索索引也没更新。

后来才弄明白。Astro 收尾的时候会删一批临时文件，我那套环境里有一层安全删除的机制，删到大概五十个文件的时候会抛错。这个错发生在一个很靠后的钩子之前，结果就是 sitemap 集成压根没执行，pagefind 也没跑。屏幕上看着是构建完成，其实后半截全丢了。这个错出在我这边的环境，跟 Astro 没关系。

更坑的是我当时误判了方向。我以为是 sitemap 集成的配置有问题，在选项上改了半天，一点效果没有。助手提醒我先确认集成到底有没有跑，加一行日志一看，根本没进去。

所以那天最该先做的，是确认代码到底有没有被执行，再去动配置。改配置没反应的时候，别在配置里死磕。

## 字体栈里的空指针

第三个坑藏得更深，是一个字体的小事故。

我用了一款动漫风的字体，全站就这一款。博客字体文件大，所以只保留了站里实际用得到的字，加上完整的英文字符，裁成一份很小的子集。这套流程本来是好的，直到有一次英文和数字忽然变得跟中文不是一个字体。

查下来，是我之前在字体栈里还写过一个圆体，专门渲染拉丁字符。后来子集化的时候，那个圆体的声明被一起删掉了，字体栈里就留了一个空指针。浏览器找不到那个字体，就静默回落到系统默认。不报错，只是悄悄换了样子。

从那以后我定了个规矩，字体栈里只写真正声明过的字体，一个都不多写。

## URL 和目录

URL 这块也有个不容易发现的地方。这个站是接在旧站后面的，二十多篇老文章的地址不能变，一变外链和搜索引擎全废。Astro 的内容加载器会把文件名里的 id 转成小写，我有篇老文章叫 edgeBBB，加载出来变成 edgebbb。查映射的时候要是拿 id 去对，永远对不上，得拿原始文件路径。

目录也折腾过一轮。最开始我想用运行时扫一遍正文的二级三级标题，拼个目录挂右边，样式用 float 加 sticky。结果目录直接飘走了，跑到评论区下面去了。

原因是 float 脱离了文档流，跟 sticky 打架。后来翻官方文档才发现，Astro 渲染文章的时候本来就把标题结构给你了，直接在服务端渲染目录就行，根本不用跑到浏览器里扫。改成两栏 flex，目录当右侧的子项做 sticky，就稳了。

现在回头看，从 Hexo 换到 Astro，框架本身的语法没花多少时间。花时间的是那些默认值、环境差异，还有看着成功其实没成功的构建。

如果你也在往 Workers 上迁，Worker 站别指望 Cloudflare 那套自动预取，它不会生效，只会给你一堆 503。构建那次更值得记住，退出码正常不代表产物完整。字体子集化这种不起眼的流程，改完要亲眼看一下英文数字有没有跳字体。

这个博客现在打开是干净的，没有红字，也没有多余的网络请求。剩下的事，是继续写东西。
